# 计划：从根基删除 match exhaustiveness 检查

## 背景与根因

最近一次提交 `8906aff` revert 了 `91622b6`（"List/Dict/Tuple pattern 覆盖公共 API + 6 单元测试"）。深层根因（通过子代理全量取证）：

1. **Mora 是「可选类型注解的渐进式静态类型」**——`docs/mora-spec.md:3/42/225`、`:66`（Lisp 反向借鉴）、`typeck/mod.rs:1`（"v11 静态类型检查"）。HM 是 v0.55 起的唯一检查器。
2. **Mora 没有 `Type::Tuple` 变体**，但 `WitnessPattern::Tuple`/`List`/`Dict` 是真实存在的 match pattern 形态（`witness.rs:354-362`），spec §7.3/§7.5 也明确描述。
3. **List/Dict 在 typeck 里携带元素/值类型**（`List<T>` / `Dict<String, V>`），元素类型/值类型走 HM 合一；但**长度/键值开放**——所以对 List/Dict/Tuple pattern 做精确 exhaustiveness 需要 type union merge 推断（估 1-2 周）。
4. v0.75.86 起 `exhaustive.rs` 实现了 Int/Float/String/Bool 4 种 literal 的覆盖度检查——对 List/Dict/Tuple 走「保守视为覆盖」分支。但**这是基于错误前提（动态类型）的「永远 None 的 stub API」**，与项目「静态类型 + 无 Tuple 类型 + 不留兼容层」原则冲突。

## 用户决策（已固化）

- **彻底删除一切 match exhaustiveness 检查**——按字面执行，不留 stub、不留未来 hook。
- **`collect_match_exhaustive_recursive` 保留为通用遍历器并重命名**——它 139 行覆盖 Binary/Call/If/List/Dict/LetBinding/Loop/While 等所有 WitnessKind，是 `check_mir.rs` 内部公共基础设施，与 match exhaustiveness 解耦。
- **「按字面量类型拆 4 文件」自动失效**——没有 checker 函数可拆，删就是删。
